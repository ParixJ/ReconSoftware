# Multi-ledger scrutiny implementation and validation

## Execution sequence

1. **Identify and parse each source.** Structured CSV, JSON, XLSX, genuine binary XLS, and Tally XML are detected from their contents. Flat, multi-sheet, repeated-ledger-section, and voucher-centric layouts are normalized using reusable mapping profiles. The `DSPVch` JSON dialect and existing multi-section Excel dialect remain compatible. Image-only AIS/TIS PDFs use local OCR; Form 26AS, GST cash/credit ledgers, tax computation, and product ledgers have separate adapters. Unsupported backups are rejected rather than misidentified.
2. **Normalize and persist evidence.** Keep the original uploaded file. Persist source metadata and issues, normalized records, ledger statements, and OCR lines in an atomic SQLite write. Index records by owner/report, collection, kind, period, ledger, and reference. Retain page/row/cell or workbook-row provenance in each normalized record. Existing embedded source rows remain readable.
3. **Validate controls before comparing.** Check AIS table counts and printed totals, Form 26AS groups, ledger subtotals/balances, GST running balances, and product quantity roll-forward. A whole-rupee AIS detail/total discrepancy of at most one rupee is explicitly marked `verified_with_rounding`; other discrepancies prevent a trusted source status.
4. **Run selected comparisons.** Existing book checks remain. `AIS02` compares verified AIS GST-turnover months with mapped dated sales-ledger movements. `A26` compares AIS TDS/TCS table controls with Form 26AS groups. `T03` compares TDS/TCS receivable movements with Form 26AS credits, and `G02` compares book CGST/SGST cash-ledger movements with portal cash-ledger heads. `X01` compares auditor-mapped book roles against available TIS, AIS, Form 26AS, GST cash/credit, and computation measures. Reference matching partitions by tax month, supports splits, and leaves unknown periods or OCR uncertainty for review. No comparison automatically matches on amount alone.
5. **Validate at the API boundary.** Upload all supplied document types through authenticated report endpoints, re-read the stored normalized sources, run checks, and assert the resulting evidence. Run unit, client, build, and browser E2E gates.

## Supplied-data boundary

`sample-docs/New Data (1)` includes the Gayatri multi-ledger workbook and its AIS, Form 26AS, computation, GST portal ledgers, and product ledger. The root `sample-docs/Tally.json` is from another company; it tests `DSPVch` parsing but must not be treated as corroborating the Gayatri books. The `.zip` and `.001` files are Tally backups, not structured audit documents. The sample AIS is image-only; its six pages take roughly two minutes to OCR on the tested machine. OCR is limited to ten pages and one concurrent upload per server process. Other AIS layouts need their own fixture-based verification before claiming table-level accuracy.

The authenticated supplied-file test is opt-in because of OCR runtime: from `server`, run `$env:SCRUTINY_REAL_SAMPLES='1'; node --test test/scrutinyRealSamples.test.js` in PowerShell. The normal `npm test` suite skips that fixture-dependent test.

The supplied Gayatri AIS scan currently exposes 45 information tables, but its GSTR-3B turnover table has 11 readable months against a printed count of 12. That table and the AIS source stay `unverified`/`insufficient_data`; `AIS02` must not assert a book-turnover match. Verified AIS TDS/TCS tables can still be shown separately in `A26` as review evidence. The Ashwin TIS OCR identifies its PAN, but unreadable detail amounts keep the source `insufficient_data`; its legible category totals remain review-only comparisons. These are source-extraction limitations, not ledger differences.
