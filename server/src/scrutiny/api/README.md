# Scrutiny audit-report API contract

All paths are under `/api/scrutiny/audit-reports` and require the existing session authentication. The server derives ownership from the session; clients must not submit an owner or reviewer ID. IDs in nested paths must belong to the same user-owned report. Successful JSON payloads use resource envelopes; failures use the shared `{ "error": { "code": "...", "message": "...", "details": ... } }` envelope.

| Method and path | Request | Successful response |
| --- | --- | --- |
| `POST /` | `{ "name": "FY audit", "fiscalYear": "2024-2025", "taxpayerId": "optional PAN or GSTIN" }` | `201 { "auditReport": AuditReport }` |
| `GET /` | none | `200 { "auditReports": AuditReport[] }` |
| `GET /:reportId` | none | `200 { "auditReport": AuditReport, "sources": AuditSource[], "runs": AuditRun[] }` |
| `GET /source-library` | none | `200 { "sources": AuditSource[] }`, most recent 1,000 owner sources for report linking |
| `GET /mapping-profiles` | none | `200 { "profiles": AuditProfile[] }` |
| `POST /mapping-profiles` | `{ "name", "role", "configuration" }` | `201 { "profile": AuditProfile }`, pending approval |
| `POST /mapping-profiles/:profileId/approve` | none | `200 { "profile": AuditProfile }`, approved and immutable |
| `POST /:reportId/sources` | multipart with one `file`, `role`, `completeExport=true/false`, optional approved `profileId` | `201 { "source": AuditSource }` |
| `POST /:reportId/sources/derive` | `{ "fromSourceId", "profileId"?: string, "completeExport": boolean }` | `201 { "source": AuditSource }`, immutable correction or cross-report link |
| `GET /:reportId/sources/:sourceId` | none | `200 { "source": AuditSource }`, including `source.parsed` when available |
| `GET /:reportId/sources/:sourceId/rows?collection=rawRows\|records&offset=0&limit=100` | none | `200 { "rows": object[], "total": number, "offset": number, "limit": number }`; limit 1–500 |
| `GET /:reportId/sources/:sourceId/preflight` | none | `200 { "preflight": { "sourceId", "parseStatus", "issues", "originalFieldNames", "previewRows", "proposedRoles" } }`; role suggestions always require auditor approval |
| `GET /:reportId/sources/:sourceId/file` | none | `200` original file bytes with stored `Content-Type` and `Cache-Control: no-store` (not JSON) |
| `POST /:reportId/runs` | `{ "selectedSourceIds": ["source-id"], "checkIds": ["B01"], "idempotencyKey": "optional-key" }` | `202 { "run": AuditRun }` |
| `GET /:reportId/runs/:runId` | none | `200 { "run": AuditRun }` |
| `GET /:reportId/runs/:runId/results` | none | `200 { "results": AuditResult[], "reviews": AuditReview[] }` |
| `GET /:reportId/runs/:runId/comparisons?offset=0&limit=100` | none | `200 { "rows": object[], "total": number, "offset": number, "limit": number }`; rows are stored with the completed run |
| `PUT /:reportId/runs/:runId/results/:resultId/decision` | `{ "decision": "needs_follow_up", "note": "Inspect original voucher" }` | `200 { "review": AuditReview }` |
| `POST /exports` | `{ "runIds": ["completed-run-id"], "format": "xlsx"\|"pdf", "grouping": "consolidated"\|"by_fy" }` | `202 { "export": AuditExport }` |
| `GET /exports/:exportId` | none | `200 { "export": AuditExport }`, status queued/running/completed/failed |
| `GET /exports/:exportId/file` | none | `200` owner-only XLSX, PDF or by-FY ZIP download |

`AuditReport` has `id`, `name`, optional `taxpayerId` (PAN or GSTIN), consecutive `fiscalYear` (`YYYY-YYYY`), `createdAt`, and `updatedAt`. Timestamps are ISO UTC. `AuditSource` includes `id`, `reportId`, `role`, optional `documentType`, `originalName`, `mimeType`, `fileType`, `sizeBytes`, `sha256`, `parserVersion`, `createdAt`, `parseStatus`, and parsing issues. Supported roles are `books_vouchers`, `books_ledgers`, `trial_balance`, `prior_year_trial_balance`, `ais`, and `supporting_document`. Structured supporting CSV/JSON/XLS/XLSX may declare `documentType` as `prior_year_report`, `msme_register`, `bank_statement`, `loan_schedule`, `stock_report`, `tax_challan`, or `tds_rules`; known PDF/XLSX support can still auto-detect. Upload one file at a time, at most 25 MB. Declare `completeExport=true` only for a complete source; without it, clean matches are withheld. The parser produces `source.parsed` with normalized records and provenance.

Book imports detect CSV, JSON, XLSX, genuine binary XLS and Tally XML from file bytes, not the filename extension. Flat tables, nested JSON record paths, multi-sheet workbooks, repeated ledger sections, and Tally voucher postings are supported. Repeated ledger sections auto-match date, particulars, voucher, debit, and credit headers within the first 100 rows after each section title; the parsed source retains section row ranges, entity heading, and address lines in `ledgerStatements`. Mapping profiles specify field labels, account roles, optional sheets/header row/section marker and JSON path. Profiles are versioned, owner-scoped, and require an explicit approval action before use. Original uploads and corrected source versions stay immutable; cross-report linking reuses the original file. The existing Gayatri workbook and non-standard Tally JSON adapters remain compatibility dialects, not the canonical ledger model. An absent opening/closing control is never inferred as zero; checks that require it return `insufficient_data`. `B05` reviews negative running balances only for auditor-mapped cash accounts; it cannot classify cash accounts or apply legal payment thresholds automatically. Ledger PDFs and proprietary backups are unsupported.

AIS PDFs are recognized from a text layer or by local English OCR when image-only. The server deployment must include the bundled English model and the platform's native canvas package; OCR does not require a runtime model download. Image-only pages are read at two resolutions; printed grid lines locate cells, and numeric cells are independently OCR-checked. The parser retains summary controls and transaction rows by table, including dates/periods, amounts, status and page/box provenance. It validates active-row counts and detail totals against each table's printed controls. A whole-rupee difference of at most one rupee across multiple whole-rupee detail rows is marked `verified_with_rounding`, not an exact match, and surfaced in `parseWarnings`. Other unreadable or inconsistent controls leave the source `insufficient_data`. `source.parsed` includes `tables`, `records`, `ocrUsed`, `pageCount`, `parseWarnings`, and `textLines`. OCR processes at most 10 pages and 16 million pixels per detailed page, with one OCR upload per server process at a time. A concurrent OCR upload returns `AUDIT_OCR_BUSY` (429) and may be retried. Text-layer PDFs without mapped tables remain `insufficient_data`; they do not silently gain trusted transaction rows.

PDF identity is extracted from the labeled identity section. Conflicting format-valid PAN/GSTIN candidates set `review`; absent candidates set `insufficient_data`. AIS section codes are normalized only in their code cell and checked against their description; SFT-016 savings/term/recurring interest and non-income SFT-005 remain separate. Unknown sections and unreadable candidate rows are retained with raw cells and page/row references. Dates require real calendar and FY/quarter consistency. OCR amount alternatives remain in `amountReading.candidates` and are selected only when printed count/total controls uniquely support them. Supporting PDFs include `labelAliasVersion` (currently 2) and report unmapped headings as coverage issues. Recognized Form 26AS sections outside the supported comparisons appear in `parseWarnings`. `identityCandidates`, `unclassifiedSections`, and `rejectedRows` are exposed in `source.parsed` where applicable.

For every upload, source metadata and parser issues are stored in `scrutiny_sources`; normalized records and original extracted rows are stored separately in the indexed, user/report-scoped `scrutiny_source_records` table. OCR/text lines are stored in `scrutiny_source_text_lines`. `scrutiny_mapping_profiles` holds approved mapping versions, `scrutiny_source_lineage` holds correction/link ancestry, and `scrutiny_exports` tracks generated files. The original evidence file remains in the audit upload store and is retrieved through the authenticated original-file endpoint. Source metadata and rows commit in one SQLite write transaction. Existing sources with embedded `parsed_json.rows` remain readable; migrations are additive.

`supporting_document` auto-detects Form 26AS, TIS, tax computation, GST electronic cash/credit ledgers, and the supported product-ledger workbook. Scanned TIS receives local OCR with page/row provenance and an OCR-review status; five common category totals and readable detail candidates are extracted, but uncertain detail cells are flagged. The computation extracts refund, income, tax credit, interest and GST turnover summaries. Explicit structured support types add prior-year reports, MSME registers, bank statements, loan schedules, stock reports, tax challans and TDS rule evidence. GST cash and credit comparisons keep IGST, CGST, SGST and cess heads distinct; they require corresponding approved book account roles. Form 26AS and GST/stock controls retain their existing validation. Binary XLS is accepted for structured ledgers; Tally backup archives and opaque `.001` files are not. The PDF text extractor reads at most 50 text-layer pages; OCR uses a bounded page count.

`AuditRun` has `id`, `reportId`, `status`, selected source IDs, check IDs, and `createdAt`; it may include `startedAt`, `finishedAt`, `error`, and results on detail fetch. Status is `queued`, `running`, `completed`, or `failed`. `X01` is the mapped-book versus supporting-source comparison across available AIS/TIS, Form 26AS, GST cash/credit ledgers and computation measures. `PY01`, `M01`, `G03`, `S02`, `BK01`, `L01`, `AT01`, and `TDS01` cover prior-report, MSME, full GST tax-head, stock-risk, bank, loan, challan and TDS-auditor review paths. Exact-reference matching partitions by tax month and supports split postings, unmatched sides and ambiguous counterparties; missing tax periods, OCR and unverified book identity stay review-only. Existing B/AIS/G/S/T checks retain their prior meanings. A run is an immutable selection snapshot; an optional `idempotencyKey` prevents duplicate creation. Export files derive from saved results, not a rerun; XLSX keeps structured comparison values and source references, while PDF prints each saved evidence object and its provenance. By-FY export is a ZIP of one file per FY.

`B06`–`B11` add reference-tool ledger candidate checks for suspense balances, debtor/creditor signs, duplicate postings with distinct voucher IDs, pending GST balances, insurance/prepaid classification, and prepaid reversals. `P02` compares current and prior-year trial-balance closings by ledger, using magnitude differences so presentation sign changes do not inflate YoY variance. These are review candidates, not tax/legal conclusions. `B08` requires explicit voucher IDs and dates; unassessable rows are counted, not silently treated as unique. Missing printed opening or closing controls stay absent even when a statement's totals balance.

Parser version 4 removes an older paired-column workbook inference that filled unprinted opening/closing controls with zero. When a previously stored paired-column source with an earlier parser version is read, its parsed view receives `AUDIT_LEGACY_BALANCE_INFERENCE`; new balance-based checks return `insufficient_data` until a corrected source revision is derived from the original file. Existing saved run snapshots are not rewritten.

Source parse status is not a blanket run gate. A source with normalized records and a non-conflicting extraction/coverage issue (for example `AUDIT_EXPORT_COMPLETENESS_UNCONFIRMED`) may participate in applicable checks. Such results are `review`, never a definitive `matched` or `difference`, and include `source_limitation` evidence with the original issue codes. A check still returns `insufficient_data` if its own required fields or controls are missing and it has no assessable finding. Conflicting taxpayer, period, role, or multi-entity evidence remains blocking. Previously saved run snapshots are not modified; run the checks again to apply this policy.

`X01` only treats AIS, TIS, Form 26AS, GST cash/credit ledgers, and computation as comparable supporting sources. Other support files feed their dedicated checks (`PY01`, `M01`, `S02`, `BK01`, `L01`, `AT01`, `TDS01`) and do not block `X01`. A relevant supporting file with no usable rows is reported as unavailable while other relevant sources can still yield `review` findings; a contradictory taxpayer or period still blocks the comparison.

`AuditResult` has `id`, `runId`, `checkId`, `status`, and `summary`. Status is `matched`, `difference`, `review`, or `insufficient_data`. Optional `expectedAmount`, `actualAmount`, and `differenceAmount` are decimal strings, never JSON numbers. Evidence points to source records. Reviewer decisions are append-only `AuditReview` events (`confirmed`, `dismissed`, or `needs_follow_up`); the server, not the request, supplies reviewer identity and decision time. Missing or incomplete comparison data must result in `insufficient_data`, never a synthetic match.

Input validation rejects unknown fields, unsupported roles/checks/decisions, empty or duplicate selections, invalid fiscal years, and oversized names/notes. Route handlers must also verify that every selected source belongs to the report and authenticated user, and that a decision targets a result belonging to the specified run. The contract validators do not replace those persistence checks.

The original-file endpoint must apply the same report/source ownership lookup before reading its stored path. It must use only the server-persisted path, not a client path, and send `Content-Disposition` safely for the original filename. It is an evidence preview/download route; no OCR or parsed-value guarantee is implied for PDFs.

The shared error catalog registers `INVALID_AUDIT_REPORT`, `INVALID_AUDIT_SOURCE_ROLE`, `INVALID_AUDIT_SELECTION`, and `INVALID_AUDIT_DECISION` for request validation; `AUDIT_REPORT_NOT_FOUND`, `AUDIT_SOURCE_NOT_FOUND`, `AUDIT_RUN_NOT_FOUND`, and `AUDIT_RESULT_NOT_FOUND` for nested lookup failures; and `AUDIT_SOURCE_INVALID`, `AUDIT_SOURCE_INCOMPLETE`, `AUDIT_OCR_BUSY`, and `AUDIT_RUN_FAILED` for processing failures. Existing authentication, upload-limit, and database-busy codes continue to apply. Validation errors include `details.issues` with `path` and `message` fields.
